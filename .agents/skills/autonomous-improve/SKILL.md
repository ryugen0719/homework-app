# Simple Autonomous Improvement Workflow

複雑なマルチエージェント構成を使わず、**1つのメインエージェント**が小さな単位で調査・改善・検証を繰り返すワークフロー。

## サイクル構造

```text
IMPLEMENT(現状把握/対象選定) → RESEARCH(調査) → REVIEW(設計・影響評価) → IMPROVE(小規模実装) → TEST(検証・記録)
```

各反復（Iteration）で以下の 8 ステップを順番に実行する。

### 実行手順

1. **現状分析（Analyze）**
   - `git status` と `docs/IMPROVEMENT-LOG.md` を確認し、前回の結果・未解決課題・進行中の作業を把握する。
   - 対象領域（コード品質、パフォーマンス、セキュリティ、UI/UX、テスト）を調査する。
2. **問題点と改善候補の発見（Identify）**
   - 事実（ファイルパス・行番号・計測値・エラーログ）に基づき改善候補をリストアップする。
   - 改善候補がなければサイクルを終了する。
3. **調査（Research）**
   - 必要に応じて `node_modules/next/dist/docs/`（Next.js 16 の最新仕様）や Web 検索でベストプラクティス・ライブラリ仕様を調査し、変更の根拠を揃える。
4. **優先順位決定とレビュー（Review & Prioritize）**
   - 影響度（ユーザー体験・安全性・保守性）と変更コストから **1サイクルにつき1つだけ** 最小スコープの改善タスクを選ぶ。
   - 既存機能を壊さないか、事前確認が必要な重大変更に該当しないかを判定する。
5. **実装（Improve）**
   - 必要最小限のファイルのみを変更する（一度に大量の変更をしない）。
6. **検証（Test）**
   - 静的検証: `npm run lint` および `npx tsc --noEmit`（必要に応じて `npm run build`）を実行する。
   - 自動テストが存在する場合はすべて実行する。
   - UI/UX に影響する変更は、ローカル開発サーバーを起動しブラウザで実動作確認する。
7. **評価（Evaluate）**
   - 改善前後の比較を行い、問題が解決したか判定する。
   - **未解決またはテスト失敗の場合**: 原因を分析して再改善（最大2回リトライ）し、再度テストする。解決できなければ変更を安全に巻き戻し、未解決課題として記録する。
8. **記録と次サイクル（Log & Next）**
   - `docs/IMPROVEMENT-LOG.md` に結果を追記する。
   - 改善候補が残っており、指定の反復回数未満であれば次のサイクルへ進む。

## 必須制約

- **既存機能を壊さない**: 変更前後の挙動が保たれていることをテスト・ビルド・ブラウザで確認する。
- **根拠のない変更をしない**: 計測値・公式ドキュメント・明確なバグ/負債を根拠にする。
- **一度に大量の変更をしない**: 1サイクル＝1テーマの小さな差分にとどめる。
- **テストを通さず完了にしない**: 最低限 `npm run lint` と `npx tsc --noEmit`（および該当テスト・画面確認）を通す。
- **重大な変更・デプロイは事前確認する**: 以下の操作は自動実行せず、必ずユーザーに確認して停止する。
  - 外部公開・デプロイ（`git push`, Vercel デプロイ等）
  - データベース（Firestore）やストレージ（Vercel Blob）のデータ削除・破壊的マイグレーション
  - 認証方式・セキュリティ方針の破壊的変更
  - 未コミットのユーザー作業ファイルの上書き
- **未解決なら再改善する**: 期待した効果が出ない、または検証に通らないまま次へ進まない。

## 完了条件

以下のいずれかを満たした時点でワークフローを完了とする。

1. 優先対応すべき改善候補がなくなった。
2. 指定された反復回数（例: `max_iterations`）に達した。
3. 人間の事前確認が必要な重大変更に到達した（確認事項を明示して停止）。
